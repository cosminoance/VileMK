# 0.3.0

- Keyboard repositories that only build through their maker's own GitHub workflow now build as fetched, without a fork: VileMK builds from a prepared copy of the repository.
- For a repository that keeps one keyboard in several folders (for example Bluetooth and dongle), the Build panel has a **folder** select. Build stays off until one is picked.
- For those repositories the Build panel lists the maker's own build entries to tick. Build stays off when none is ticked, or when the same half is ticked twice.
- The build sheet lists the maker's settings files from its `config/` folder (such as the one that turns a trackball on), ticked the way the maker's build uses them.
- After fetching a module, the keyboards sheet lists the drivers its own config pulls in, each with a tick and a branch or tag. The branch made for this project's ZMK version is preselected when the driver has one.
- A module with no `*.zmk.yml` for its keyboard is now in **Add a keyboard**, named after its shields and marked "no metadata".
- A keymap started from a maker's keymap that includes a file from their `config/` folder (such as `macros.dtsi`) now builds; the file is copied in next to the keymap.
- When a maker's own build changes their keymap for the folder you build, **Build** now asks whether to make the same change. Your keymap file is not touched. Saying yes fixes the Charybdis Bluetooth build failing on `vtrackball`.
- When a maker's own build fetches drivers this project does not have (such as the trackball driver for Charybdis), **Build** now lists them first and offers to add them before building. Before, the build failed partway through on settings it did not recognise.
